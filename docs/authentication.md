# ავტორიზაცია

დოკუმენტი აღწერს აპლიკაციის ავტორიზაციის არქიტექტურას ზედა დონეზე — როგორ შედის მომხმარებელი სისტემაში და რა გზები არსებობს. ტექნიკური დეტალები მინიმალურადაა.

## მიმოხილვა

ავტორიზაციის 4 გზა არსებობს:

1. **პაროლით შესვლა** — მომხმარებლის სახელი + პაროლი
2. **OTP** — ერთჯერადი კოდი (ზედმეტი დაცვის შრე)
3. **Face ID / თითის ანაბეჭდი** — ბიომეტრიული შესვლა
4. **გასანდოება** — მოწყობილობის სანდოდ დამახსოვრება (passkey / WebAuthn)

ყველა გზა ბოლოს ერთსა და იმავე შედეგს აღწევს — **სესიის ტოკენს** (session token), რომლითაც მომხმარებელი ავტორიზებულად ითვლება.

## ზოგადი პრინციპი

- ბექენდი თავად წყვეტს შესვლის სცენარს. `/sessions`-ზე მოთხოვნის პასუხში ბრუნდება ტიპი:
  - `SESSION` — ჩვეულებრივი შესვლა, ტოკენი მზადაა
  - `OTP` — საჭიროა ერთჯერადი კოდის დადასტურება
  - `PWD_CHNG` — პაროლის სავალდებულო შეცვლა
- მიღებული ტოკენი ინახება **დაცულ საცავში** (`expo-secure-store` მობილურზე, `localStorage` ვებზე).
- ყველა შემდგომ მოთხოვნას ტოკენი ავტომატურად ერთვის `Authorization: Bearer <token>` სახით.

## 1. პაროლით შესვლა

1. მომხმარებელი შეაქვს სახელი და პაროლი.
2. აპლიკაცია აგზავნის მოთხოვნას `/sessions`-ზე.
3. ბექენდი პასუხში აბრუნებს ტოკენის ტიპს:
   - `SESSION` → შესვლა დასრულდა, გადადის მთავარ გვერდზე
   - `OTP` → იხსნება OTP ფანჯარა (იხ. ქვემოთ)
   - `PWD_CHNG` → იხსნება პაროლის შეცვლის ფანჯარა
4. წარმატების შემთხვევაში ტოკენი და მომხმარებლის პროფილი ინახება დაცულ საცავში.

## 2. OTP (ერთჯერადი კოდი)

1. თუ შესვლისას ბექენდი აბრუნებს `OTP` ტიპს, მომხმარებელი იღებს კოდს (მაგ. SMS-ით).
2. იხსნება კოდის შეყვანის ფანჯარა, სადაც მოქმედებს ~3 წუთიანი ტაიმერი.
3. კოდი იგზავნება ბექენდზე დასადასტურებლად.
4. დადასტურების შემდეგ ბრუნდება სრული სესიის ტოკენი და შესვლა სრულდება.

> OTP ტოკენი დროებითია — მოქმედებს მხოლოდ კოდის დადასტურებისთვის და იცვლება სრული სესიის ტოკენით.

## 3. Face ID / თითის ანაბეჭდი

**ჩართვა (ერთჯერადად):**
- ავტორიზებული მომხმარებელი ჩართავს Face ID-ს.
- მოწყობილობის ბიომეტრიის დადასტურების შემდეგ მისი მონაცემები ინახება დაცულ საცავში.

**შესვლა:**
1. მომხმარებელი ამოწმებს ბიომეტრიას (Face ID / ანაბეჭდი / PIN).
2. წარმატების შემდეგ საცავიდან იკითხება შენახული მონაცემები.
3. ამ მონაცემებით ხდება ჩვეულებრივი პაროლით შესვლა — `/sessions`-ზე.

> მონაცემები ინახება მხოლოდ მოწყობილობაზე და ბიომეტრიით იშიფრება; სერვერზე არ იგზავნება. თუ შესვლა ვერ ხერხდება არასწორი მონაცემების გამო, Face ID ავტომატურად ითიშება.

## 4. გასანდოება (მოწყობილობის სანდოობა / Passkey)

ეფუძნება WebAuthn სტანდარტს — მოწყობილობა იქცევა სანდო "გასაღებად" და შესვლა შესაძლებელია პაროლის გარეშე.

**რეგისტრაცია (მოწყობილობის გასანდოება):**
1. შესვლის შემდეგ, თუ მოწყობილობა ჯერ არ არის სანდო, ჩნდება შეთავაზება.
2. აპლიკაცია ბექენდიდან იღებს "გამოწვევას" (challenge).
3. მოწყობილობა ქმნის passkey-ს (ბიომეტრიის/PIN-ის დადასტურებით).
4. შექმნილი passkey იგზავნება ბექენდზე და ინახება.
5. მოწყობილობა ხდება სანდო.

**შესვლა გასანდოებით:**
1. მომხმარებელი აჭერს "გასანდოების" ღილაკს.
2. ბექენდი გასცემს გამოწვევას.
3. მოწყობილობა ხელს აწერს ბიომეტრიით/PIN-ით.
4. ხელმოწერა მოწმდება ბექენდზე და ბრუნდება სრული სესიის ტოკენი.

**მართვა:**
- პროფილში ჩანს სანდო მოწყობილობების სია და შესაძლებელია მათი გაუქმება.
- აპის გახსნისას ხდება ლოკალური მდგომარეობის სინქრონიზაცია ბექენდთან (მაგ. აპის თავიდან დაყენების შემდეგ აღდგენისთვის).

## სესიის შენახვა

| მონაცემი | სად ინახება |
|----------|-------------|
| სესიის ტოკენი | დაცული საცავი (`expo-secure-store` / `localStorage`) |
| მომხმარებლის პროფილი | დაცული საცავი |
| Face ID მონაცემები | დაცული საცავი (მხოლოდ მოწყობილობაზე) |
| Passkey ID | დაცული საცავი (მხოლოდ მოწყობილობაზე) |

## ნაკადების შეჯამება

| გზა | შესვლის წერტილი | შედეგი |
|-----|------------------|--------|
| პაროლი | შესვლის ფორმა | სესიის ტოკენი / OTP / პაროლის შეცვლა |
| OTP | კოდის ფანჯარა | სესიის ტოკენი |
| Face ID | ბიომეტრიის ღილაკი | სესიის ტოკენი |
| გასანდოება | passkey ღილაკი | სესიის ტოკენი |
